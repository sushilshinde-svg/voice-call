# Voice Call — Anonymous Voice Chat

Live demo: [https://voice-call-three.vercel.app/](https://voice-call-three.vercel.app/)

Voice Call is a minimal, privacy-first web app whose sole purpose is to let two (or more) people talk anonymously over the web. No accounts, no phone numbers, no usernames — just a short unique code that you exchange with someone and you can begin a voice chat.

This README explains what the app does, how it works, how to use it, deployment/installation notes, privacy considerations, common troubleshooting steps, and ideas for improvements.

## Core idea

Voice Call provides a frictionless way for people to talk anonymously. Each session is represented by a short unique code (e.g. `AB12-XY`) generated by the app. Share that code with another person and they can join the same session and speak in real time. The app intentionally avoids identity systems and keeps the UX focused on immediate, ephemeral voice communication.

---

## Key features

- Anonymous voice-only chat (no accounts).
- Short unique join codes to connect callers.
- Browser-based — works on modern desktop and mobile browsers.
- Minimal UI: create a room, get a code, share it, join by code.
- Mute/unmute, speaker volume control.
- Ephemeral sessions — no long-term storage of audio (implementation-dependent).
- Optional indicators for active microphone/speakers.

---

## How it works (user flow)

1. Alice opens the app and clicks "Create call" (or "Generate code").
2. App generates a short unique code (the "room code") and shows it to Alice.
3. Alice copies or shares the code with Bob (e.g., chat, SMS, voice).
4. Bob opens the app, selects "Join call", and enters the code.
5. Both browsers request microphone access. After granting permission, browsers connect and voice is exchanged in real time.
6. When the call ends, participants close the page or click "Leave" — the session is torn down and code becomes invalid/expired.

## How it works (technical overview)

This section describes a typical, recommended implementation. Your repository may implement these components differently — adapt as needed.

- Signaling:
  - A small signaling server (WebSocket/HTTP) is needed to exchange session metadata (SDP offers/answers and ICE candidates) between peers. The signaling server is not used for audio transfer; it's only used to negotiate the connection.
- Media transport:
  - WebRTC is the recommended transport for browser-to-browser real-time audio. WebRTC handles encoding, peer-to-peer connectivity, and fallbacks through STUN/TURN.
- NAT traversal:
  - STUN servers allow discovery of public endpoints. For reliable connectivity across restrictive networks, a TURN server is recommended so audio can be relayed when direct peer-to-peer isn't possible.
- Room code generation:
  - The server (or client, with server validation) generates an unguessable short code (for example: 6–8 alphanumeric characters, optionally grouped: `XX-YY-ZZ`) and maps it to a temporary session on the signaling server.
  - Codes should have a short expiry (minutes to hours) to prevent reuse and reduce abuse.
- Session lifecycle:
  - When a code is created, an entry is stored in-memory or in a short-lived store with a created timestamp and optional participant list.
  - When another peer joins with the code, signaling begins and WebRTC peer connections are established.
  - After all participants leave or the expiry is reached, the session is cleaned up.
- Privacy:
  - The app should not store audio on the server. Signaling messages and metadata may be logged for debugging but should not contain audio data.
  - If server-side logs are kept, they should be rotated and minimal. Use HTTPS and WSS to protect signaling traffic in transit.
- Optional features:
  - TURN server for reliability (coturn).
  - Rate-limiting and abuse protection (CAPTCHA, per-IP rate limiting).
  - Optional moderation or recording features (only if users are notified and consent).

## Using the app

Live app: [https://voice-call-three.vercel.app/](https://voice-call-three.vercel.app/)

Typical usage:

1. Open the app in your browser.
2. Click "Create Call" or "Generate Code".
3. Copy or share the code shown on screen (e.g., `KJ8L-ZQ`).
4. The other person opens the same link, enters the code in "Join call", and connects.
5. Both users must allow microphone access.
6. Use the in-call controls to mute/unmute or leave.

Tips:
- Use headphones to avoid echo.
- If one side cannot connect, ask both participants to retry or switch networks (mobile data vs Wi-Fi).
- If the browser asks for microphone access, you must accept it to send audio.

## Permissions & browser behavior

- Microphone: required to send audio. Browsers will prompt the user for access the first time.
- Browser compatibility: modern versions of Chrome, Firefox, Edge, and Safari generally support WebRTC. Some mobile browsers may have limited support.
- HTTPS is required for microphone access and reliable WebRTC behavior in most browsers — deploy over HTTPS for production.

---

## Security & privacy

Privacy is a primary design goal. Recommended best practices:

- No user accounts — sessions are anonymous.
- Do not persist audio on the server by default.
- Use secure transport (HTTPS/WSS) for both UI and signaling.
- Short code lifetimes and unguessable codes reduce chance of random joins.
- Implement rate-limiting and abuse controls to prevent automated scraping or DoS.
- If you add recording or logging features, surface an explicit notice and obtain consent.

Important note: "Anonymous" does not mean guaranteed untraceable. Network operators, hosting providers, or law enforcement may be able to obtain connection metadata. If strong anonymity is required, provide clear documentation and warnings.

---

## Limitations & known issues

- Connection reliability depends on network/NAT conditions. TURN servers are required for the most reliable experience.
- Browser support may vary — encourage users to use modern browsers.
- No identity means no persistent moderation or blocking across sessions.
- Spam/abuse risk if codes are posted publicly — consider adding optional gating (simple CAPTCHA, ephemeral passwords).

## Local development / Run locally

Below is a simple, generic set of steps to run the app locally. Adapt commands to your repository tools (npm/yarn/pnpm) and server stack.

1. Clone the repo:
   - git clone https://github.com/sushilshinde-svg/voice-call.git
   - cd voice-call

2. Install dependencies:
   - npm install
   - or
   - yarn install

3. Start the signaling server (if present):
   - cd server
   - npm run dev
   - (Check server README for exact commands.)

4. Start the frontend:
   - cd client
   - npm run dev
   - default: open http://localhost:3000

5. Ensure your local dev server is served over HTTPS if testing microphone access in some browsers. Tools like mkcert or the dev server's HTTPS options can help.

If your repo is a single static app relying on a hosted signaling endpoint, set the signaling server URL in a `.env` file:

- .env
  - REACT_APP_SIGNALING_URL=wss://your-signaling.example.com
  - REACT_APP_TURN_URL=turn:turn.example.com
  - REACT_APP_TURN_USER=username
  - REACT_APP_TURN_PASS=password

## Deployment

This app can be deployed as a static frontend (Vercel, Netlify) plus a small signaling server (VPS, Heroku, Railway, or serverless web socket provider). For production:

- Host the frontend over HTTPS (Vercel is already used: [https://voice-call-three.vercel.app/](https://voice-call-three.vercel.app/)).
- Host a reliable signaling server (Node/Express + ws/socket.io or serverless alternatives).
- Configure STUN and TURN servers (coturn) for robust NAT traversal.
- Protect the signaling endpoint with sensible rate limits and basic abuse protections.
- Use environment variables for keys and secrets; do not commit them.

## Testing & troubleshooting

- If you get "no microphone detected", check browser permissions and hardware.
- If you can hear but others can't, verify microphone is unmuted and the browser is allowed to use it.
- If you cannot connect at all, ensure signaling server URL is correct and reachable.
- Use browser devtools console to view WebRTC/ signaling logs.
- For NAT issues, verify TURN server is configured and reachable.

## FAQ

Q: Is this truly anonymous?
A: The app requires no sign-up and no usernames, but network metadata (IP addresses) and server logs may identify users. Use the app over VPN if you need additional network-level privacy. Always read the privacy policy of any deployed instance.

Q: Does the app record voice?
A: By default the app should not record or store audio on the server. If you add recording, inform users and obtain consent.

Q: Can I use this on mobile?
A: Yes — modern mobile browsers with WebRTC support should work, but behavior varies by browser and OS.
